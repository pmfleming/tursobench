The tiling rules

Start from a binary split tree, then let content influence each split. The native implementation evaluates both views’ width needs before opening, using schema columns before the first rows arrive. A wide table may split below the whole group; narrow tables favor side-by-side placement. Choose the axis and ratio that expose the most useful content, with a penalty for horizontal scrolling and undersized panes. Opening a view is explicit; receiving rows never shuffles windows.

  • Minimums, then tabs: provisional native minimums: grid 420 × 200, structure 260 × 180, map 320 × 220, SQL 460 × 200, record 280 × 180 logical pixels. Measure them against system font size and scale. The embedded demo uses smaller minimums to remain usable inside this conversation.
  • Move windows: in the native app, drag a title to a tile edge to split, its center to swap, or Shift+center to group tabs. The outer workspace edges place across the whole side. Escape cancels. Right-click titles for movement options; Ctrl Alt Shift + arrow moves to a workspace edge.
  • Preserve intent: drag splitters, with minimums enforced; manually sized splits stay fixed until Retile. Closing a window collapses its branch. Expanding stores the tree and selected tabs; Restore returns to that exact arrangement. No floating overlays over the grid.
  • Small display / many views: group new windows into tabs when no viable split exists. All views remain reachable from the left navigator. On resize, temporarily collapse unsuitable branches into groups and restore the saved tree when space returns.
  • Focus is explicit: a title, border and ribbon label identify the command target. Opening a view while expanded restores the tiled workspace and focuses the new view. Keyboard proposals: Ctrl Shift Enter expand/restore, Esc restore, Ctrl Tab next view; the native implementation must check existing bindings.
One ribbon; controls stay close to their purpose

Use the app’s existing line icons with visible text and 40–44 px action targets. One row of grouped commands, not a multi-row office toolbar. On narrow screens, keep Open view and Expand visible, and move secondary actions to a labelled More menu. The HTML specimen scrolls its ribbon to let you inspect all groups.

Theme evidence and the native egui approach

Observed on this machine: Hyprland / Wayland, GTK 3 Adwaita-dark with a generated palette override, dark mode reported by the desktop portal. The portal currently exposes color-scheme and contrast, but no accent color. The blue and surface colors below come from the GTK CSS, not from a guessed “dark theme”.

Surface #000000Controls #141b22Focus #2f8cffText #d7dee8
  • Source evidence: ~/.config/gtk-3.0/settings.ini, ~/.config/gtk-3.0/gtk.css, GTK 4 settings, org.freedesktop.portal.Settings.ReadAll, and fc-match. Fonts resolve to Noto Sans and JetBrains Mono Nerd Font. The CSS uses 3 px control corners and blue outlines on active tabs.
  • Preference: add AppearanceMode::{System, Light, Dark, Custom}. Default to System. Migrate the old dark_mode value without silently changing an explicitly saved preference; show a one-time “Follow system” choice for existing users.
  • Resolve: explicit app override first, then platform appearance signals; use platform palette adapters where available. On this Linux setup, resolve the named GTK colors used above as a bounded fallback when the portal omits them. A few parsed named colors are not full GTK theme support. Unsupported theme expressions use a neutral light/dark fallback.
  • Apply: replace hard-coded emerald assignments in appearance.rs with semantic roles mapped into egui::Visuals. Keep the existing asynchronous system-font discovery. Observe palette, scheme and scale changes off the UI thread and request repaint.
  • Contrast: respect the system high-contrast preference and validate text, selection and focus independently. The subtle machine border should gain a stronger accessible variant. Keep state labels and icon shapes; color alone must not encode focus, keys or write access.

The browser’s “Follow system” option demonstrates light/dark changes only; a browser cannot read arbitrary GTK palette files. “This machine” is a captured palette specimen. “Light” is a proposed neutral fallback, not a claim about a detected light palette.

Implementation plan grounded in this repository

Keep the native egui application. This HTML is a reviewable interaction model, not a proposal to replace it with a web frontend. The essential architectural change is separate retained view state: today App has one result, table, browse, sql and active request. Drawing several copies of the current view would not create independent windows.
